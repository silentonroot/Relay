- **B2 must guarantee** (the B1 repositories rely on it and cannot enforce it):

    from a request, a stored record or an earlier step. The database clock bounds a wrong value
    (5 seconds at issue, `statement_timestamp()` at consume), but a stale `now` still skews audit
    timestamps and the unused part of the window.

    open checks, and the audit append (`vault.secret_read`, `vault.secret_stored` or

    taken by the consume is held until that transaction commits and a failure of any later step
    rolls the consume back.

    token MAC check follows the consume inside the same transaction.

    handling.** When a job's outcome invalidates a session (`reauth_required`, `identity_mismatch`,
    or no stored session) the supervisor deletes the stored versions (`vault.deleteForConnection`)
    and revokes the connection's unused capabilities (`capabilities.revokeForConnection`, reason

    opens or seals anything here; a connection has one running job at a time per worker claim, so
    the delete cannot race a read of the same session by that job; it shares the transaction with

    issued earlier is bound to the secret and version at issue (the seal binding), so a revoked or
    deleted secret fails any later consume. The "vault is the only caller of `capabilities.*`"
    rule above therefore has this one worker-side caller, for revocation only.

runs the real stack of the Phase 2 test (PostgreSQL, the vault as a fourth process with `shared-uid`

the vault in the path of every read. The shared set-up moved to `test/e2e/harness.ts`, used by both files;
`phase2.e2e.test.ts` kept its steps and passed 15/15 after the move. Vitest runs files one after the other
(`fileParallelism: false`), and each run has its own database, directories and display, so the two files
share no port, database or socket (the demo port 4100 is free again when a file ends).

**Status: passed in a recorded nightly run.** Local run: one machine, 2026-11-20, PostgreSQL 17. Recorded
run: nightly run 44898131882 (scheduled, 2026-11-21, commit 4efa110, which contains all of B6). Its End-to-end
test job succeeded with `NORTHSTAR_DEMO_REPOSITORY` set: the demo checkout, the runner preparation with

Steps (all synthetic data; the worker holds no key):

1. **real login and read through the vault.** Two real login handoffs and a real `orders.list`. The
   capability row shows issue and consume, the audit chain the stored secret, the issued capability and the
   read, and a proxy on the worker's vault socket saw `completeLogin`, `issueAccessCapability` and
   `readForWorker`.
2. **worker asks the vault for an unrelated connection.** The worker is paused and the test speaks on the
   real supervisor socket. Job A's read token is presented for Bob's connection, for `orders.get`, for job
   B, and as a login completion: four refusals with `binding_mismatch`, the capability row unchanged, then
   the same token accepted with its own bindings and the spent token refused as `used`. A secret version
   made active after the issue gives `secret_not_active`; a job moved to another worker or attempt gives
   `binding_mismatch`; issue for another worker or attempt is refused. VS-5: issue for an unknown
   capability (`unknown_token`), for another job's capability, for a job with no authorization and for an
   authorization edited by a database writer (`integrity`), each with no token. Every refusal is the plain
   `forbidden` answer, one `vault.capability_rejected` event with the expected reason, and 14 events in
   all.
3. **revocation during a running job.** Two interleavings, both through the real API and worker (the
   worker runs with its default lease in steps 0 to 3a; only for 3b is it restarted, through the same
   proxy, with a short lease, after a check that the old worker and its sandboxes are gone):
   (a) between the token issue and the consume: the proxy holds the worker's `readForWorker`, the
   connection is revoked through `POST /connections/:id/revoke`, the line is released. The test
   requires the vault branch: the proxy counts forwarded `readForWorker` lines, and the test asserts
   that the held line was forwarded and produced exactly one `vault.capability_rejected` event with
   reason `revoked` (it fails with a message naming the other branch if the job was cancelled before
   the vault judged the token); then the job ends without a read, no browser starts, the capability is
   revoked and unused, the secret is `revoked` and its versions are gone; (b) after the consume, with
   the browser holding the session: the sandbox and every process below the worker are frozen with
   `SIGSTOP`, the connection is revoked, and the worker's heartbeat (every 2 s with
   `AAB_WORKER_LEASE_MS=6000`) sees the flag and ends the job. Before anything is resumed the test
   asserts that every frozen process has exited: a stopped process cannot exit by itself and nothing
   else signals it, so the heartbeat that ends the job also kills the sandbox (a process that is gone
   or a zombie waiting to be reaped counts as exited). What this proves is that the heartbeat ends the
   job and the worker takes the sandbox down; it does not prove that the revocation reached a
   browser that was running (it was frozen). No request reached the demo after the freeze. The freeze
   is wrapped in `try`/`finally`: whatever happens, the frozen pids are resumed and then killed if
   alive, and they are in the watchdog's spec (with the proxy directory `<socketDir>-proxy`) so that a
   killed test process leaves nothing stopped.
4. **no token, MAC or plaintext in logs, responses, audit or any column.** About 955 needles (raw tokens
   including those the real worker presented, plaintext session values read through the vault and every
   session the proxy saw the worker log in or read, step 3b's included, the demo and owner passwords, the
   dashboard session cookie and CSRF token, token hashes, token MACs, authorization MACs; each in raw,

   response, the vault's answers to refused requests, audit metadata, job rows and every column of 15
   tables (168 columns, about 170 rows). The three columns that hold hashes and MACs are excluded for
   hash and MAC needles only, and the API's own responses for the dashboard cookie and CSRF token (the
   API returns them to their client); the test asserts the hash and MAC columns are the only ones that
   contain one, and that the CSRF token is in the responses (so the exclusion is needed) and would be found if it
   appeared in a log. Positive controls cover every new form. The vault runs at debug level, as the worker does; before
   the scan the test triggers a role-refused `readForWorker` (with a real token) on the api socket, a
   role-refused `rewrap` on the supervisor socket and an oversized line, and asserts that the vault log

**Trust boundaries to check.**

- **Sockets per role.** `api` (authorize), `supervisor` (issue, read, complete login) and `admin`
  (status, rewrap, retirement check), one directory and one socket each, group per role in
  `separate-uid`. The socket is the identity: no request field selects a role. Questions: can any
  process outside the role's group connect; can any request field, ordering or connection reuse cross
  roles; does the protocol layer parse before it checks the role anywhere it should not.
- **Database writer.** Any service that holds the shared database role can read and write every table,
  including capability rows, job rows and ciphertext. The design answer is the two MACs (a forged or
  edited row yields no token) and the AAD (a moved version does not open); a writer can still delete
  rows, restore a backup (VS-12) and disable the revocation trigger as table owner.
- **Sandbox.** The runner must not reach any vault socket (P3-14, VS-14): bubblewrap and Docker mount
  nothing under the socket directory. The `unsafe-process` launcher shares the supervisor's user and is
  refused unless `shared-uid`.
- **Key directory.** Readable only by the vault's user; the API and the supervisor refuse to start when
  they can open it (`separate-uid`) or when `AAB_KEK_DIR` is set; the vault never deletes a key file.

**Invariants and abuse cases to verify.** P3-1 to P3-20 of section 1 and the abuse cases VS-1 to VS-22 of
[`threat-model.md`](threat-model.md) section 4.10, plus VA-6, VA-11, VA-12 and PE-14, using the
coverage map above as the index of existing tests. The reviewer should try to break, not only read:
replay and race a token, present a token for another job, connection, operation, purpose, worker,
attempt or version, edit a capability row, move a ciphertext row, restore an older version, kill the

event and column for a token, a MAC or a plaintext. Check that each test in the map asserts what its
name says (B6a and B6b record which bodies were read and which were not) and that a mutation of the
code under test fails it.

**Known residuals the review should judge, not rediscover.**

1. **Shared database role.** One role serves every service, so any service can write capability, job
   and audit rows and read ciphertext columns. Accepted for Phase 3 (owner decision 4); the Phase 9
   ticket is AAB-036.
2. **`separate-uid` was tested with a stand-in.** The start-up probes ran against a stand-in vault, and
   group ownership of real sockets runs only where the test user has three extra groups. No test
   connects from a third uid (VS-9): it needs a second account. The `shared-uid` mode protects nothing
   against code running as the service user, by design.
3. **The Docker launcher is root-equivalent** (VS-19, owner decision 7). Under it the supervisor can
   reach the key directory; bubblewrap is the only launcher the claims apply to.
4. **Installation-wide counts on the key-status page (L7).** `GET /v1/vault/status` and the dashboard's
   key-status page show installation-wide values (versions per KEK version and the vault's counters,
   including rejection counters across all organizations) to the owner of any organization, because
   the vault and its key are one per installation. Fine for a single owner; restrict the route to an
   installation administrator before any multi-tenant use.
5. **The race test mirrors the revocation route.** `services/vault/test/revocation-race.test.ts`
   reproduces the route's transaction order (and has a test that compares its copy with the route); a
   change to the route that the copy does not follow would not be caught by that file. The real route is
   covered by the end-to-end test and by `lifecycle-audit.test.ts`.
6. **Refusal rate-limit windows.** `vault.capability_rejected` is appended at most 60 times per
   organization per minute (`REJECTIONS_PER_WINDOW`) and `vault.request_refused` at most 60 times per
   60 second window (`services/vault/src/refusals.ts`); beyond that the events are logged and counted,
   so a flood hides individual refusals behind a count. Rejections whose job id does not resolve are
   logged and counted, not chained (VS-11, owner decision 9).
7. **A revoke does not interrupt a running read before the next heartbeat (B6b).** The end-to-end test
   shows the worker ends the job when its heartbeat sees the revocation (every 2 s with a 6 s lease, in
   step 3b of the test only). With the default 60 second lease the heartbeat runs every 20 seconds, longer than the
   15 second timeout of the Northstar operations, so a read that has already consumed its capability
   can finish before the worker looks (reasoned from the settings, not tested); the secret and its
   versions are deleted at revocation, and no new read can start.
8. **Rollback from a backup is not detected** (VS-12, VA-11): the vault keeps no record of the newest
   version outside the database.
9. **A compromised supervisor reads the sessions of the jobs it claims** (VS-5) and can skip its own
   argument-hash check (VS-17); a compromised API can authorize capabilities for jobs it creates.
10. **A spent or revoked capability can be re-armed by a database writer (VS-1, B6 review finding
    L5).** `used_at` and `revoked_at` are not under either MAC, so a writer who also holds a spent token
    can set `used_at = NULL` and redeem it again inside its windows, and clearing `revoked_at` of a
    capability revoked while its connection and secret are still active reopens it likewise. The token
    hash, the bindings, the windows, the running job and the connection and secret status checks of the
    same statement still apply. Documented by a test, not fixed (a production change); the fix is to put
    those states inside the MAC or in an append-only record.
11. **Smaller points recorded in this document set:** `unknown_token` events can add noise to a chain
    for anyone who holds a job id (VS-11); redaction is heuristic (DB-8); job results sit in plaintext
    in the database (AAB-029, outside the vault); no caller pid in vault audit records (owner decision

## 4. Open questions for the owner

_Answered on 2026-11-16: the owner accepted the recommendation for every question below. Question 4 (separate database roles per service) becomes a Phase 9 ticket._

1. **Peer credentials versus per-role sockets.** ADR-014 uses socket file permissions per role and no
   native module. Recommendation: accept; add a peer-credential module later only if pids in vault
   audit records are wanted, after an ADR-012 review.
2. **Default isolation for local installs.** `separate-uid` needs root once to create users, groups
   and directories. Recommendation: keep it the default and documented; allow `shared-uid` only by
   explicit setting, with the warning and the dashboard indicator.
3. **Retries after a session was handed out.** ADR-014 drops automatic requeue of a read once its
   capability was issued. Recommendation: accept for Phase 3 (reads only, agent resubmits); revisit
   with Phase 7 orchestration.
4. **Separate database roles.** One role lets any service write capability rows, jobs and audit
   events. Recommendation: keep the MAC in Phase 3 and plan per-service roles (vault owns the vault
   tables; others get no access to ciphertext columns) for Phase 9; a ticket now.
5. **The vault completes login jobs and activates the connection.** This keeps the seal and the
   activation in one transaction at the cost of connection writes in the vault. Recommendation:
   accept.
6. **Authorization lifetime default (600 s).** A job queued longer fails with `vault_denied`.
   Recommendation: accept for single-owner volumes; make it a setting within the 10 s to 1 h bound.
7. **Docker launcher and uid separation.** With the Docker launcher the supervisor is
   root-equivalent. Recommendation: say so in `security.md`; treat bubblewrap as the only launcher the
   supervisor claims apply to until a rootless engine is evaluated.
8. **Migration numbering.** The Phase 3 task list named migration 0003 for B1, but `0003_phase2_execution` exists.
   Recommendation: `0004` for the arguments hash (B0.5) and `0005` for the vault (B1).
9. **Rejections that name no resolvable organization** are logged and counted, not chained.
   Recommendation: accept for a single organization; revisit with multi-tenant work.
